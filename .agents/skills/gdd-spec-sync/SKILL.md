# GDD Spec Sync (`game_design_document_gdd_godot_4.md`, `races_design_v0.5.md` & `lore_and_story.md`)

Три главных дизайн-документа проекта занимают более 2 200 строк (`708` строк в GDD + `1 326` строк в `races_design_v0.5.md` + `166` строк в `lore_and_story.md`). Этот скилл позволяет:
1. Не сжигать контекст полным чтением всех документов на каждой задаче.
2. Не нарушать границы вех (`v0.2` / `v0.5` / `v1.0`) и стоп-лист раздела `14.6`.
3. Быстро выявлять и закрывать расхождения (дрейф) между кодом, тестами и GDD.

## Шаг 1. Гейт по вехе (Scope Check) — ДО написания кода

Откройте [spec_map.md](./references/spec_map.md) и определите:
1. К какой вехе относится задача (`v0.2` макет, `v0.5` альфа, `v1.0` релиз).
2. Не попадает ли механика в **Стоп-лист** (раздел `14.6` GDD, строки `703–708`).
   - Если пользователь **явно** просит перенести фичу из `v0.5` в текущий этап — предупредите о расширении скоупа и зафиксируйте это в GDD после реализации.
   - Если задача про `v0.2` — **не генерируйте** массовый контент `v0.5/v1.0` (каталоги заклинаний, 22 расы, экономику, `SaveManager`, `MindDomain`).

## Шаг 2. Точечное извлечение спецификации (Progressive Disclosure)

Вместо чтения GDD целиком откройте только нужные диапазоны строк из [spec_map.md](./references/spec_map.md):
- Для формул времени и темпа: GDD `2.3` (`L45–77`) + `12.1` (`L466–484`).
- Для статов, циркуляции и `REG`: GDD `2.1–2.2` (`L19–44`), `3.1–3.2` (`L86–176`), `12.3` (`L499–505`).
- Для боя, 4 барьеров, клэша и Ауры: GDD `7.1–7.4` (`L340–403`), `12.2` (`L485–498`), `14.4` (`L664–677`).
- Для анатомии и травм: GDD `3.4` (`L193–236`), `12.4` (`L506–510`).
- Для этажей, полёта, HUD, аудио и управления: GDD `12.6–12.8` (`L515–563`), `14.3` (`L655–663`), `14.5` (`L678–702`).
- Для рас `v0.5`: нужная раса по таблице строк в [spec_map.md](./references/spec_map.md) (не загружайте все 1 326 строк `races_design_v0.5.md` ради одной расы).
- Для лора и сюжета (`v0.5/v1.0`): ориентируйтесь на `lore_and_story.md` по таблице строк в [spec_map.md](./references/spec_map.md).

Перед редактированием кода сверьте формулы из GDD с **живыми скриптами** в `project/src/` — если баланс уже правился в коде (например, коэффициенты Ауры в `PenetrationResolver.gd`), опирайтесь на подтверждённый баланс кода и отметьте необходимость синхронизации GDD.

## Шаг 3. Автоматический аудит дрейфа (Drift Audit)

Запустите скрипт [check_spec_drift.py](./scripts/check_spec_drift.py):

```powershell
python "d:\My game\.agents\skills\gdd-spec-sync\scripts\check_spec_drift.py"
```

Скрипт проверяет без запуска Godot:
1. Число сьютов в `project/tests/run_tests.gd` против упоминаний числа сьютов в GDD (`12.8`, `13.1`, `14.2`).
2. Все действия `[input]` в `project/project.godot` против карты управления в GDD `14.5` (подсвечивает отсутствующие или устаревшие статусы «зарезервировано»).
3. Состав `[autoload]` и ровно `18` именованных слоёв `[layer_names]` в `project.godot` против GDD `12.6` / `12.8`.
4. Ключевые балансные константы в `PenetrationResolver.gd` (Аура, `AURA_MP_PER_SEC`, `AURA_BURST_MULT`) против формул в GDD `12.2`.
5. Все файлы `.tres` в `project/data/` против тестового набора оружия в GDD `14.4`.

## Шаг 4. Синхронизация GDD после завершения фичи

Обновляйте `game_design_document_gdd_godot_4.md` **только после зелёного прогона** `godot-test-and-verify`:
1. Обновите число наборов и ассертов в разделах `12.8`, `13.1` и `14.2` (точные цифры из `SUMMARY:` последнего прогона).
2. Если добавлена/изменена клавиша `InputMap` — обновите раздел `14.5` (перенесите из «Зарезервировано» в актуальный список).
3. Если изменены балансные формулы или константы — обновите разделы `3.1`/`3.2`/`12.2`/`14.4` и `combat-balance-lab/references/benchmarks.md`.
4. Если фича переведена из «спроектировано» в «реализовано» — обновите разделы `12.9`, `13.1` и `14.1`.
5. Повторно запустите `check_spec_drift.py` и убедитесь, что новых предупреждений дрейфа нет (или задокументированы осознанные расхождения).
